## **꼭 지켜줬으면 하는 것 [<u>매우 중요]</u>**

- 아래 branch naming에 맞게 브랜치 이름을 정하기. ( e.g. fix_24 )
- 폴더나 파일의 **위치 이동, 삭제**는 팀원들에게 말하고 하기
- **푸쉬하기 전에 `git pull origin main` 해서 원격 레포의 main 변경사항을 반영 한 뒤에 충돌을 각자 미리 해결하기**

### **권장사항**

    - 이슈나 pr에 자신이 한 기능과 맞는 라벨을 붙이면 좋음
    - 작업할때 한 브랜치에 너무 많은 변경을 하는건 비추. 나중에 충돌 엄청생김
    - 작업할때 커밋을 중간 중간 하는걸 추천. 커밋을 기점으로 되돌아 가는식으로 개발하면 편함
    - **폴더 생성, 파일생성**은 **자유**롭게 해도 됨. 근데 **위치 이동, 삭제**는 팀원들에게 말하고 하기
    - git add 할때 직접 파일 하나 하나 지정하기 (**`git add .**` 하면 내가 예상하지 못한 게 깃에 올라갈 수 있음)
        - 요지는 깃에 올리고 싶은 파일만 add하는 것
    - 자기가 짠 코드를 이해하기
    - 자신이 짠 코드로 문제가 생길경우 본인이 직접 문제 해결
    
    #### **이슈 이름 : #{이슈번호} {브랜치 접두사}: {자신이 할 작업}**
    

## **git workflow**

1. 이슈 생성 (내용에 자기가 작업할 내용 적기, 자세히 적을 수록 좋음)→
2. 이슈탭에서 브랜치 생성 →
3. 해당 브랜치에서 작업 →
4. git pull origin main 해서 충돌 미리 해결 →
5. 문제 없으면 자기 작업브랜치에푸쉬 →
6. pr생성 버튼 눌러서 pr생성 →
7. 리뷰어 선택
    - 경우 1. 변경사항이 다른 팀원 누구와도 관련 없다 -> 자기 자신을 리뷰어로 지정 (총 리뷰어 1명)
    - 경우 2. 변경사항이 다른 팀원 n명과 관련 있다 -> n명의 다른 팀원 모두를 리뷰어로 지정 (총 리뷰어 n명)
8. 현재 메인을 기준으로 백업 브랜치 만들기
    - 이름 규칙: backup_{날짜}_{자신이 작업한 브랜치 이름}
    - e.g. backup_10-30_feat_3
9. 리뷰 후 머지
    - 경우 7-1. 자기 자신이 직접 pr "approve" 후 자신이 머지
    - 경우 7-2. 모든리뷰어가 "approve" 후 가장 마지막에 "approve"한 리뷰어가 머지

## **깃 명령어 정리**

- 로컬 레포지토리에 생성한 브랜치를 그대로 생성

`git checkout -b sample-branch origin/sample-branch`

- 로컬 워크스페이스가 어느 원격 레포랑 연결되었는지 확인

`git remote -v`

(이때 origin 보여야 함)

- 자신의 워크 스페이스에 main 의 원격에 있는 변경사항을 반영

`git pull origin main`

## **branch naming**

접두사_이슈번호

**접두사**

- 기능추가 : feat
- 코드 수정: refactor
- 버그 픽스: fix
- 문서,주석 작성: docs
